# 🛠️ 三场景优化方案

---

## 1️⃣ 爬多个网页

### ❌ 错误方式
```
你：爬这 10 个网页然后分析对比
我：web_fetch × 10 → 40k tokens 直接打入历史
```

### ✅ 正确方式

**方案 A：分批 + 写文件**
```
1. 我：分批爬取（每次 3-5 个）
2. 我：原始内容写 `memory/raw-data/xxx.md`
3. 我：只保留摘要在对话中（每网页 200 tokens）
4. 用户需要细节时，我再从文件读取
```

**方案 B：只用摘要**
```
1. 用户指定要的信息字段
2. 我：爬取 → 只提取关键信息 → 汇总表格
3. 原始内容不保留
```

**方案 C：用 subagent**
```
1. 我：spawn 一个 isolated subagent 专门爬取
2. subagent：爬完汇总后返回
3. subagent 的对话历史不会污染主会话
```

## 2️⃣ 代码审查/分析

### ❌ 错误方式
```
你：分析整个项目
我：读文件 1 → 分析 → 读文件 2 → 分析...
→ 每个文件 3k tokens，10 个文件就 30k
```

### ✅ 正确方式

**方案 A：目标导向**
```
1. 你先说：要关注什么问题？（性能？安全？架构？）
2. 我：只读取相关模块（不是全部）
3. 汇总写 `memory/code-review.md`
```

**方案 B：分层分析**
```
1. 第一层：只看项目结构 + README + 主要入口
2. 第二层：针对问题深入具体文件
3. 避免一次性读太多
```

**方案 C：用 subagent**
```
1. 代码分析 spawn 独立 session
2. 分析完生成报告
3. 主会话只收报告，不收过程
```

---

## 3️⃣ 写代码

### ❌ 错误方式
```
你：写一个功能
我：读上下文 → 写 → 修改 → 再读上下文 → 再修改...
→ 上下文反复读入
```

### ✅ 正确方式

**方案 A：最小上下文原则**
```
1. 只读真正需要的文件（不是整个项目）
2. 用 `read offset/limit` 只读相关部分
3. 写代码时不重复读文件
```

**方案 B：草稿文件**
```
1. 复杂逻辑先写 `memory/scratchpad.md`
2. 反复修改草稿（不污染对话）
3. 最后一次性写代码
```

**方案 C：分段实现**
```
1. 大功能拆成小模块
2. 每个模块独立实现
3. 最后集成
```

## 🎯 通用最佳实践

### 1. **及时写文件**
```
对话中：大量中间数据
→ 写 `memory/xxx.md`
→ 对话只保留摘要
```

### 2. **用 subagent 隔离**
```
主会话：只发指令 + 收结果
Subagent：干脏活累活（爬取、分析）
```

### 3. **明确范围**
```
❌ "分析这个项目"
✅ "只看 src/api 和 src/models 两个目录"
```

## 📋 建议的工作流模板

### 爬网页任务
```
用户：爬这 N 个网页，关注 XXX 信息
我：
  ├─ 分批爬取（3-5 个一批）
  ├─ 原始内容 → memory/raw-data/
  ├─ 对话只保留摘要
  └─ 最后汇总
```

### 代码分析任务
```
用户：分析 XXX 问题
我：
  ├─ 问清楚范围（哪些文件/模块）
  ├─ 生成分析大纲 → memory/analysis-plan.md
  ├─ 按大纲逐步深入
  └─ 汇总报告 → memory/analysis-result.md
```

### 写代码任务
```
用户：实现 XXX 功能
我：
  ├─ 设计草稿 → memory/draft.md
  ├─ 读取最小必要文件
  ├─ 分段实现
  └─ 测试反馈循环
```
